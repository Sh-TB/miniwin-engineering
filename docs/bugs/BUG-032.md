# BUG-032 — CRT stdio stream pointers are `_iob`-structured, not glibc FILE*

**Status:** CLOSED (TESTED, 2026-10-15, EXP-040)
**Priority:** P0 (every classic-msvcrt PE uses stdio)
**Discovered:** appcompat sweep stage 3 (t01 SIGSEGV inside glibc setvbuf)

## Symptom

After wave-1 APIs resolved, t01 crashed at RIP inside libc. Trace tail:
`__iob_func() = 0x2023180` then `setvbuf(stream=0x20231e0, mode=4->2, size=0)`
followed by the fault — 0x20231e0 = iob_array + 0x60 was dereferenced as a
glibc FILE.

## Root cause

Classic msvcrt/mingw CRTs treat `__iob_func()`'s return as `FILE*` into an
**array of FILE structs** with stride `sizeof(FILE) = 0x30` on x64:
`stdin = base+0x00`, `stdout = base+0x30`, `stderr = base+0x60`. The loader's
`__iob_func` returned a 24-byte array of three glibc `FILE*` values, so every
PE-side stdio pointer was a synthetic offset into loader .data that glibc must
never dereference. Legacy wrappers defaulted unknown streams to stdout, which
masked the bug for UPX (printf/puts only) but broke any direct stream use, and
additionally sent stderr output to stdout.

## Fix

`map_crt_stream()` (loader.c, BUG-032 block): recognizes the
`[g_iob_array, g_iob_array+0x90)` window, maps offset/0x30 →
stdin/stdout/stderr; NULL passes through; anything else keeps the legacy
stdout fallback. Applied to fflush/fputs/fputc/fwrite/getc/ungetc/setvbuf.
`g_iob_array` hoisted to file scope so `__iob_func` and the mapper agree.

## Verification

- t01..t07 stdio paths all PASS post-fix (sweep run-20261015_053015).
- Regression 12/12; UPX G1 gate exit 0 (unchanged behavior).
- Trace shows `map_crt_stream: iob+0x30 -> stdout` and correct stream routing.
