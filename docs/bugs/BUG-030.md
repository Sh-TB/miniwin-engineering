# BUG-030 — landing pad resumed without the catch selector in RDX

**Status:** VERIFIED FIXED (2026-10-15, EXP-038)
**Priority:** P0 (blocker on the acceptance path, discovered post-API-005)

## Symptom

With EH hacks OFF (clean GCC personality path, EXP-038 §3), the landing pad
0x40331c resumed with correct RSP (`est−0x68`, alloc_total=0x68) and RAX=object,
but RDX=0 (raise-time value from the helper's `xor edx,edx`). The catch's
selector switch `mov rbx,rdx; …; sub rbx,1; jne <assert-failure>` took the
failure branch → UPX's own assertion print → terminate → abort (exit 134).

## Root cause (ground truth, EXP-038 §4)

The GCC SEH bridge's site A passes `arg3 = &EXCEPTION_RECORD` (not a CONTEXT)
carrying the 4-parameter protocol `param = {object, target_est, landing_pad,
selector}`: the bridge's phase engine (0x4AFDB0) stores the selector at
`obj−0x24` during phase 1, writes it into blob slot 1 (`0x49d270(blob,1,sel)`)
during phase 2, and the site-A setup copies `blob[1] → ER.param[3]`
(0x49d4f6–0x49d528). The bridge's `flags&0x20` branch independently writes
`ctx->Rdx(+0x88) = ER.param[3]` — param[3] IS the RDX selector. Our
`mw_RtlUnwindEx` set RAX from arg4 but never delivered RDX.

## Fix

`src/loader/loader.c` `mw_RtlUnwindEx` — fingerprint-guarded, protocol-driven:

```c
if (er_nparams == 4 && er_params[1] == tgt_frame && er_params[2] == tgt_ip)
    *(uint64_t*)(ctx + CTX_Rdx) = er_params[3];   /* catch selector */
```

No app-specific constants; the guard validates the protocol shape live.

## Verification

- Trace: `RtlUnwindEx: 4-param protocol ER (obj=… est=… lp=0x40331c sel=1) -> CTX.Rdx=1`.
- Post-resume: selector branch TAKEN (`call 0x4dfce0` now executes in the trace) —
  the failure point moved strictly later (protocol-state check) = BUG-031.
- Regression **12/12** (test 10 expectation evolved with evidence comment).
- Hacks-ON backward-compat preserved (BUG-029-era behavior byte-identical).
