# BUG-065 — md5deep64 4.4 wave: CRT-init surface, VirtualProtect EXEC bits, argv[0] dispatch, stream validation

**Status:** PARTIALLY CLOSED — four sub-fixes VERIFIED; md5deep itself remains
RUNS-PARTIAL with a documented frontier (see bottom).
**Discovered by:** LADDER-013 (md5deep64 4.4, 2014 mingw64/msvcrt, SHA
4994759f…, official github.com/jessek/hashdeep release asset).

## Sub-fix 1: 15 unresolved imports + 3 data imports (VERIFIED)

Old-mingw CRT surface blocked startup (SIGSEGV 0x42eac9 during CRT init):
- Data: `__argv` (= &g_argv_cell), `__mb_cur_max` (=1, SBCS), `__pioinfo`
  (full msvcrt ioinfo layout: 64-slot pointer array, 2×32 ioinfo blocks of
  16 B, fd 0/1/2 = FH_DEVICE|open) — built by a loader constructor.
- Code: `_atoi64`, `_ftime`, `_wfindfirst64`/`_wfindnext64` (own 552-byte
  `_wfinddata64_t` registry + case-insensitive wildcard matcher), `getwc`,
  `iswalpha`, `iswdigit`, `sprintf` (ms_abi variadic via __builtin_ms_va_list),
  `_snwprintf` (wide fmt → narrow rewrite + UTF-16 arg conversion), `_mktemp`,
  `MessageBoxW` (console-honest stderr log, returns IDOK), `_wstat64`
  (wide wrapper over the BUG-061 `_stat64` layout writer).

## Sub-fix 2: VirtualProtect EXEC bits + honest old-protect (VERIFIED)

mingw's pseudo-relocator does VirtualProtect(.text, RWX) then RESTORES with
the value we report. Two bugs: PAGE_EXECUTE* (0x10/0x20/0x40/0x80) did not
map to PROT_EXEC, and *old was hardcoded 0x04 — the restore then made .text
non-executable (md5deep SIGSEGV at the instruction right after the call).
Now: EXEC bits honored; *old = PAGE_EXECUTE_READWRITE for image pages.
Also: the image is mapped per-section, so one mprotect over
[addr, addr+size) can span UNMAPPED gaps → ENOMEM → mingw aborts with
"VirtualProtect failed". mprotect now walks page-by-page and skips gaps.

## Sub-fix 3: argv[0] = basename (VERIFIED)

md5deep 4.4 cuts "deep" IN PLACE inside argv[0] and strcmps the remainder
("md5deep64.exe" → "md5"). With a full-path argv[0] that dispatch prints
"Unknown algorithm: …". argv[0] is now the basename (also the right model
for busybox-style multi-call, LADDER-007).

## Sub-fix 4: FILE* issuance registry (VERIFIED, caught a regression)

map_crt_stream used to pass UNKNOWN stream pointers verbatim to glibc, which
aborts the process ("Fatal error: glibc detected an invalid stdio handle").
Now every FILE* the loader issues (fopen/_wfopen/_fdopen/_fsopen + std) is
registered; unknown pointers are refused as NULL with a loud trace.
**Regression caught by the re-verify discipline:** zstd LADDER-008 dropped to
139 3/3 because zstd opens its OUTPUT via `_open` + `_fdopen` — and the
fdopen'd FILE* was never registered. `_fdopen`/`_fsopen`/`_wfopen` now
register; zstd round trip re-verified 3/3 exit 0 (evidence
LADDER-008_roundtrip_20261017_152850), lz4 3/3 (…_152900), G1 12/12
(g1/20261017_152900).

## Open frontier: md5deep display-thread output line (RUNS-PARTIAL)

md5deep64 runs to completion: exit 0, correct argv dispatch, hashing pipeline
active (workers fread 8192-byte chunks through winpthreads threads, output
line of 62 B is formatted) — but the final stdout line is deterministically
lost: main returns while the winpthreads display worker is still waiting on
its queue semaphore (trace: worker in WaitForSingleObject(sem), main exits).
Later attempts reach a glibc "invalid stdio handle" abort after
WaitForMultipleObjects — an unvalidated stdio path still exists somewhere in
the winpthreads shutdown sequence. Next steps (next session):
1. Audit every mw_* stdio function for direct glibc calls that bypass
   map_crt_stream (fclose pass-through branch is a known suspect).
2. Trace winpthreads pthread_join/kill_all_workers protocol against our
   semaphore/event/CV implementations (pthread-win32 seed-state semantics).
3. Optionally add per-thread stream ownership checks.
