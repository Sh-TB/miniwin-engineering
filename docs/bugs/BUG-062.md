# BUG-062 — guest thread creation stubs → zstd MT livelock (hang ≥ 0x60000 input)

**Status:** CLOSED — TESTED (2026-10-17)
**Ladder impact:** LADDER-008 (zstd.exe) PLANNED → **VERIFIED**
**Discovery:** continuation session "ادامه" while validating LADDER-008 with the
new `scripts/ladder_run.sh` 3× evidence harness (payload 401408 bytes).

## Symptom

`zstd.exe -q -f <input>` hangs forever when the input file is **≥ 393216 bytes
(0x60000)** and exits cleanly below it. Content-independent (zeros reproduce it),
level-independent (-1/-3/-19/--fast=100 all hang), independent of stdout vs file
output (`-c` hangs too), and `zstd -t` on a .zst larger than the threshold hangs
as well. `--version` and the 1 KB–385 024 byte range all work (3× exit 0).

## Diagnosis chain (all steps reproducible, no guessing)

1. **Size bisection** — 0x5E000 OK / 0x5FFFF OK / 0x60000 hang; zeros hang too.
2. **api_trace.json tail** — infinite repeating cycle:
   `EnterCriticalSection(queue) → Leave → EnterCriticalSection(B) →
   WakeConditionVariable(CV) → Leave`, then silence.
3. **ptrace on the live hang** — first attempt attached to the WRONG process:
   `pgrep -f` matched the `/usr/bin/timeout` wrapper (whose cmdline embeds the
   same strings), which *legitimately* blocks in `rt_sigsuspend` — a red
   herring that cost one iteration. Correct targeting via `pgrep -x
   minwin_loader` shows syscall **202 = futex** with a frozen RIP inside
   glibc's cancellable-wait trampoline = the guest main thread parked in
   `SleepConditionVariableCS(..., INFINITE)` waiting for a completion that can
   never be signaled.
4. **Root cause** — `mw__beginthreadex` and `mw_CreateThread` were honest
   failure stubs ("no guest threading"): `POOL_create` in zstd got **zero
   workers**, ZSTDMT still queued jobs and the CLI waited on the job-completed
   condition variable forever. Small inputs take zstd's serial path, which is
   why only ≥ 0x60000 hangs. Additionally `mw_ExitThread` called host `exit()`
   (kills the whole process instead of the calling thread).

## Fix (loader.c only)

Thread registry + ms_abi bridge, colocated before `mw_WaitForSingleObject`:

- `MwThread g_mw_threads[64]` + `alloc_handle()`-issued opaque HANDLEs.
- `mw_thread_trampoline` (host SysV) calls the guest start routine through an
  **ms_abi function-pointer type** (`MwGuestStart`) so x64-Windows register
  passing + shadow space are generated at the call site.
- Completion via normal return **or** `mw__endthreadex` sets `done`/`exit_code`
  under `t_exit_mu` and broadcasts `t_exit_cv`.
- `mw_WaitForSingleObject` honors thread handles: real wait, `WAIT_OBJECT_0` /
  `WAIT_TIMEOUT(0x102)`; non-thread handles keep legacy passthrough.
- `mw_CreateThread` = same registry (CREATE_SUSPENDED ignored, documented);
  `mw_ExitThread` now ends the calling thread only; `mw_GetExitCodeThread`
  reports the recorded code; `mw_CloseHandle` releases finished slots.
- Threads are created detached (no join resource leak).

Documented limitations: TLS slots shared across threads; no per-thread CRT
init (fine for plain-C worker threads); stack size parameter ignored.
