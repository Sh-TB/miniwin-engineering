# BUG-039 — x64 unwind code replay restored nonvolatile registers from the
# WRONG stack slot (PUSH_NONVOL read-after-increment) and the landing-pad
# resume used the search-walk context whose target-frame codes had already
# clobbered the throw-time registers

**Status:** CLOSED (TESTED 2026-10-15) — see Acceptance below
**Priority:** P0 (root cause of the BUG-038 t08/probe C++ EH failures)
**Discovered:** live-trace debugging of t08_probe_exc.exe / t08_big_cpp_stl.exe
**Supersedes:** the BUG-038 "libunwind placeholder TargetIp" hypothesis for the
GNU-mingw fixture family (BUG-038 stays open for the llvm-mingw/MS-ER family)

## Symptom (pre-fix)

- `t08_probe_exc.exe`: p1 (catch int) OK, but p2 (catch std::string&) printed
  `len=0 content=` and p3 (catch std::exception&) printed `BAD`; the probe's
  `ok` counter was clobbered with a heap pointer (`PROBE ok=46681368/3`).
- `t08_big_cpp_stl.exe`: `RESULT score=159 expected=255` (r0=32 + r1=64
  missing — the catch(int) and catch(std::string&) returns were wrong).

## Root cause 1 — PUSH_NONVOL restore read one slot too high (BUG-039/A)

The unwind-code array is stored in DESCENDING code-offset order, i.e. already
in undo (epilog) order. Each push code must therefore restore the register
from the CURRENT Rsp BEFORE advancing (ReactOS `sdk/lib/rtl/amd64/unwind.c`
`PopReg`: `SetRegFromStackValue(Context, Reg, Rsp); Rsp += 8;`).

All three replay sites in the loader incremented FIRST and read AFTER:

```c
new_rsp += 8;
*(uint64_t*)(ctx + off) = *(uint64_t*)(new_rsp);   /* WRONG slot */
```

**Live proof** (evidence/master/bug039/, t08_probe p1 unwind, Frame[1]
`__cxa_throw` RF 0x209f0, codes ALLOC_SMALL 0x20 @0x07 + PUSH rbx/rsi/rdi
@0x03/0x02/0x01): with the increment-first order the restored registers were
`RDI=[E1]=0x140020af1` — the RETURN ADDRESS slot — while the real saved rdi
sits at `[E1-8]`. After the fix the same frame restores
`RDI=&got(stack), RSI=0x14002302f (the "str-exc" literal), RBP=1 (ok counter)`
— exactly main's throw-time values required by the p2 landing pad.

Fixed sites (read BEFORE increment, ReactOS PopReg semantics):
- `seh_internal_virtual_unwind` main replay loop
- `seh_internal_virtual_unwind` CHAININFO replay loop
- `mw_RtlVirtualUnwind` replay loop

## Root cause 2 — resume used a context whose TARGET-frame codes already ran
(BUG-039/B)

The dispatcher search loop unwinds the live CONTEXT through EVERY frame,
including the frame that owns the handler. By the time the personality calls
RtlUnwindEx, the live CONTEXT's nonvolatives hold the TARGET'S CALLER's
values (live proof: t08_probe p2 unwind — Frame[1] restored the correct
throw-time registers, then Frame[2] (main) replay clobbered RDI/RBP/RSI to
CRT-startup values `RDI=0x370dd38 RBP=0x370dd30`). Real Windows never resumes
a landing pad from that state — RtlUnwindEx re-walks from its own machine
state and STOPS AT the target frame.

Fix (src/loader/loader.c):
- dispatcher search loop: per-frame `pre_unwind_ctx` snapshot taken BEFORE
  `seh_internal_virtual_unwind`; when the frame owns the handler, the
  snapshot is kept in `g_target_frame_ctx` (`g_target_frame_ctx_valid=1`),
  reset per fresh dispatch.
- `mw_RtlUnwindEx` site-A path: when a snapshot is valid, all 16 GPR fields
  are copied from it into the resume context BEFORE the landing-pad protocol
  overrides (RIP=TargetIp, RSP=post-prologue, RAX=object, RDX=selector).
  RIP/RSP/RAX/RDX are overridden immediately afterwards, so the copy is
  semantically a register BASE restore only.

## Semantic rule (Issue #1 §7.2/§7.4)

1. Unwind-code arrays are consumed in undo order: `reg = [Rsp]; Rsp += 8`
   per UWOP_PUSH_NONVOL (ReactOS PopReg is the reference implementation).
2. A landing pad resumes with the target frame's THROW-TIME register state
   ("returned into frame F from below"), never with the state unwound
   THROUGH frame F (MS x64 EH doc: the context at target delivery belongs to
   the target frame; RtlUnwindEx rebuilds caller state only for the frames
   between the raise and the target).
