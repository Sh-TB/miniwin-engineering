# BUG-034 — CRITICAL_SECTION implementation writes 8 bytes past the 40-byte contract

**Status:** CLOSED (TESTED, 2026-10-15, EXP-040)
**Priority:** P0 (silent PE data corruption)
**Discovered:** appcompat sweep (t01 crash inside PE `__Balloc_D2A` after
`InitializeCriticalSection(dtoa_CritSec)`)

## Symptom

t01's mingw-ansi stdio dtoa crashed at `mov (%rax),%r8` with RAX=1 —
`freelist[0]` (PE .data) contained 1 right after the loader logged
`InitializeCriticalSection(0x14000b178)` ×2. In the PE, dtoa's
CRITICAL_SECTION sits at 0x14000b178 and `freelist[]` begins exactly at
+0x28 = 0x14000b1a0.

## Root cause

```c
struct MwCritSec { pthread_mutex_t mutex; /* 40 bytes */ int initialized; };
```
= 48 bytes. Windows CRITICAL_SECTION is **exactly 40 bytes on x64** and PEs
place it flush against other globals. `mcs->initialized = 1` wrote at
offset 40 → 8-byte overflow into the adjacent PE variable
(freelist[0] = 0x00000001). The memset guard after it was dead code
(cs_total(40) > sizeof(48) is false).

## Fix

Contract: **never write past byte 40.**
- `pthread_mutex_t` overlays the CRITICAL_SECTION memory itself.
- The "initialized" sentinel lives in the Windows SpinCount slot (offset
  36), which is zero-initialized caller-side: magic 0x4D574353 ("MWCS").
- `InitializeCriticalSection` idempotent via the sentinel;
  `DeleteCriticalSection` destroys and clears it; Enter/Leave/TryEnter use
  `cs_is_initialized` (lazy init preserved).

## Verification

- t01 runs to completion: dtoa lock no longer corrupts freelist; floats
  print (combined with BUG-033 fix); PASS.
- Regression 12/12; UPX G1 gate exit 0.
