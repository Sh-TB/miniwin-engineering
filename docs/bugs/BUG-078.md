# BUG-078 — procexp64 past the resolved frontier: unnamed stub + jump-into-string

**Status:** OPEN (one stub, one crash; runtime-image decode blocked)
**Found:** SWEEP-022 first observed; SWEEP-023 re-verified + context captured
**Supersedes:** the SW-964/SW-1000 "name procexp64 0x14006c328" open item.

## Signature (artifacts/sweep023/sweep/procexp64/run1/)

```
[STUB] unresolved import called -> returning 0 (call #1) guest_rip=0x14006c328
[CRASH] Signal 11 at RIP=0x6f00690074006e
  [RIP-MAP] no mapping contains RIP
```

## Analysis

- The crash RIP 0x6f00690074006e is UTF-16LE ASCII: bytes 6E 00 74 00 69 00 6F
  = "ntio" — a tail of a wide string like "...function..."/"...ntion...". After
  the unresolved stub returned 0, the guest read a struct field that still
  holds a string pointer and called through it → PC lands inside a string
  constant. This is the classic "stub 0 used as fn-ptr/table base" crash.
- Static decode of guest_rip 0x14006c328 is IMPOSSIBLE against the dl/ file:
  procexp64.exe is UPX-packed (SWEEP-019 note), runtime bytes differ. Bytes at
  rip-6 in the packed file (`74 16 ... 8b 8d f8 00 00 00`) are mid-instruction
  garbage. The name requires either (a) a MINWIN_FUNC_MAP exported from the
  UNPACKED image (sweep011_funcmap_export.py against the unpacked dump), or
  (b) runtime IAT dump at stub time.
- This is still REAL progress: SWEEP-022 marked the first stub call past the
  resolved frontier; SWEEP-023 confirms it deterministic (x3, call #1 each).

## Acceptance (when fixed)

procexp64 exits 0 (or advances to a NEW named stub), no Signal 11, main
window painted.
