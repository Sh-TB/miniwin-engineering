# BUG-063 — ms_abi variadic printf family used SysV va_start → garbage arg slots

**Status:** CLOSED — TESTED (2026-10-17)
**Discovered by:** LADDER-009 (lz4.exe 1.10.0) — first program whose stdout
path hits the broken arg-count shape.

## Symptom

`lz4.exe --version` → SIGSEGV inside the LOADER (not the guest): crash at
`mw_fprintf+0x1b0` (RIP 0x202ab43, loader exec region), during the format
walk. Programs with 1-arg printf calls (UPX banner) had survived for weeks —
the SysV register-save layout happened to alias the MS one for that shape.

## Root cause

`mw_printf` / `mw_fprintf` / `mw_fwprintf` are declared
`__attribute__((ms_abi)) ... (...)` VARIADIC functions but collected their
arguments with SysV `va_list ap; va_start(ap, fmt); va_arg(...)`.
For ms_abi functions gcc requires `__builtin_ms_va_list` (Windows x64: 4 GP
regs RCX/RDX/R8/R9 + shadow space, XMM volatile) — the SysV walk read the
wrong save-area layout and dereferenced wild pointers.

## Fix

`__builtin_ms_va_list` + `__builtin_ms_va_start/__builtin_ms_va_end` in all
three; arg slots still filled through the existing `mw_printf_classify`
(GP/FP classifier) and repacked by `mw_printf_emit` into a synthetic SysV
`va_list` for glibc `vfprintf` (that part was already correct).
Note: `__builtin_ms_va_arg` does not exist; gcc dispatches `va_arg(ap, T)`
correctly based on `ap`'s type being `__builtin_ms_va_list`.

## Acceptance

- lz4.exe --version exit 0 3/3 (banner "lz4 v1.10.0 64-bit multithread")
- G1 pin 12/12 (UPX banner unchanged)
- Offender scan (scriptable): all `ms_abi` + `va_start` sites now use
  `__builtin_ms_va_start` — zero remaining.
