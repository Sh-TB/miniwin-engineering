MiniWin Master Engineering Campaign — Evidence-Driven Windows x86/x64 PE Execution, UPX Unpacking, Exception Unwinding, Runtime APIs, and Reproducible Compatibility

1. Mission and Required Outcome

This is a master engineering and verification issue for continuing MiniWin from the actual current repository state, consolidating previous work, identifying the next real compatibility blockers, and improving general-purpose Windows executable compatibility.

The objective is not to make a few selected test programs pass through special cases. The objective is to build a reusable, testable execution foundation that can run increasingly complex native Windows applications and demonstrate correct behavior.

The work must cover the complete path:

PE parsing → image loading → memory and relocations → imports and exports → CPU/ABI execution → Windows API semantics → exceptions and stack unwinding → C/C++ runtime behavior → application execution → observable output → regression and compatibility measurement.

UPX-packed executables are an important end-to-end target because they exercise several of these layers together. However, the project must also retain and expand support for ordinary unpacked executables and older x86 programs.

This issue must be treated as an ongoing engineering campaign, not as permission to close the work after the first successful build or regression run.

Definition of success

Success requires all of the following:

  1. The current repository, branch, commits, existing issues, previous investigation notes, and actual implementation state have been verified.

  2. Every claimed fix is connected to the code implementing it and a regression test that would fail if the fix were reverted.

  3. The x86 and x64 execution paths are independently assessed, with architecture limitations explicitly recorded.

  4. UPX execution advances through real unpacking and reaches the original program's intended behavior, not merely a later instruction or exception handler.

  5. Standard C and C++ programs execute through reusable runtime semantics rather than application-specific patches.

  6. Failures are classified by their first genuine compatibility divergence, with reproducible traces and supporting evidence.

  7. Existing completed work is verified and closed where appropriate; unresolved, duplicate, blocked, and superseded issues are reconciled against repository evidence.

  8. A clean continuation record enables the next engineer or agent to resume without repeating investigations or relying on unverified claims.

3. Evidence and Reporting Contract

No task may be marked complete solely because code was edited, compilation succeeded, a test executable exited, or a log contains the word PASS.

Every significant compatibility fix must follow this chain:

Observed failure → source and trace investigation → identified semantic rule → minimal implementation → focused regression → broader regression → actual runtime observation → evidence record.

3.1 Allowed status values

Use these status values consistently:

  • IMPLEMENTED: Code changes are present.

  • TESTED: A specified test was actually executed.

  • OBSERVED: The stated runtime behavior was directly observed.

  • PARTIAL: Some acceptance criteria are met, but others remain.

  • BLOCKED: A concrete prerequisite prevents progress.

  • PENDING: Work or verification has not been completed.

  • SUPERSEDED: A newer verified implementation or issue replaces this item.

A test must not be described as passed if it was skipped, timed out, failed to launch, ran a stale binary, or exercised a different architecture.

3.2 Evidence requirements

For each fix, record:

  • Source file and relevant function or symbol.

  • Exact root cause and affected semantic rule.

  • Previous failing behavior.

  • Reproduction command and test artifact.

  • Before-and-after result.

  • Exit status, signal, exception code, or failure location as applicable.

  • Actual runtime trace and first divergence.

  • Test binary SHA-256 and source/build commit.

  • Number of repetitions and outcomes.

  • Regression results for related applications.

  • Remaining limitations and confidence level.

Use real screenshots, output files, memory observations, or runtime traces where appropriate. A screenshot is useful evidence but is not a substitute for verifying application behavior.

Required artifacts:

  • artifacts/evidence/

  • artifacts/logs/

  • artifacts/results/

  • artifacts/reports/

If the project already has a different artifact convention, preserve it and document the mapping rather than creating an unnecessary second system.

4. Preserve Both x86 and x64

Older Windows programs are a first-class compatibility target.

Do not remove, silently disable, or de-prioritize x86 support simply because recent investigation focused on x64 exceptions or UPX.

Maintain separate architecture results:

Target | Required treatment -- | -- x86 PE32 | Preserve and test the existing supported execution path; include older applications. x64 PE32+ | Continue advanced native execution, Windows x64 ABI, unwind, and C++ runtime work. Unsupported architecture or format | Record the exact prerequisite or unsupported feature; do not misclassify it as an unrelated runtime defect.

For every test artifact, record PE machine type, PE32/PE32+ format, subsystem, imported DLLs, entry point, and relevant runtime requirements before execution.

Use the architecture supported by the test harness and host for the intended test. If the host or execution backend cannot run a target architecture, record that as an environment prerequisite. Do not count a non-runnable artifact as a runtime regression failure without identifying the actual cause.

Where practical, maintain separate x86 and x64 baselines, test suites, and compatibility reports.

5. Workstream A — PE Loading and Executable Image Correctness

Audit the full loading path, not just the entry point.

Investigate and test:

  • DOS and PE signatures and header validation.

  • PE32 versus PE32+ parsing.

  • Machine architecture and subsystem.

  • Section table bounds and characteristics.

  • Image base and preferred versus actual load address.

  • Section mapping, alignment, zero-filled virtual tails, and access permissions.

  • Base relocation processing.

  • Import and export directory parsing.

  • Forwarded exports and ordinal imports.

  • Import thunk resolution and pointer-width correctness.

  • TLS directories and callbacks, where supported.

  • Entry-point transfer and initial register/stack state.

  • Data directories, exception directory, and load-configuration requirements.

  • Malformed-image handling and out-of-bounds protections.

For every feature, determine whether the project already implements it before adding new code.

Do not implement speculative features simply because they are part of the PE specification. First establish a concrete failing target, a relevant specification requirement, and a regression test.

Acceptance criteria

  • Valid PE32 and PE32+ fixtures load according to their supported semantics.

  • Malformed inputs fail deterministically without corrupting unrelated runtime state.

  • Relocations and imports are validated with fixtures that require them.

  • Existing application tests do not regress.

  • Unsupported cases are classified accurately.

6. Workstream B — Windows x64 ABI and CPU Semantics

Audit the CPU execution and calling convention implementation.

Verify, where relevant:

  • Integer and floating-point register handling.

  • Register preservation across calls.

  • Stack alignment and caller-provided shadow space.

  • Argument passing and return values.

  • Volatile and nonvolatile register semantics.

  • Integer arithmetic, flags, branches, and conditional operations.

  • SIMD and floating-point operations used by the test corpus.

  • Indirect calls, indirect jumps, and function pointers.

  • Instruction decoding and execution faults.

  • Context preservation at function and exception boundaries.

Do not add an opcode merely because a target crashed at a particular RVA. Decode the actual instruction, identify its required semantics, and determine whether the failure belongs to the CPU engine, ABI layer, exception path, or runtime API.

Acceptance criteria

A failing instruction has a reproducible minimal fixture. Its semantics are tested independently, and the fix is validated against the original failing application plus a relevant regression set.

7. Workstream C — x64 Exception Handling and UNWIND_INFO

This is a priority workstream because incorrect unwind metadata can break stack walking, exception dispatch, C++ destructors, and recovery from exceptions.

Use Microsoft's official documentation as a semantic reference:

  • https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64

  • https://learn.microsoft.com/en-us/cpp/build/prolog-and-epilog

Additional independent implementation references may include LLVM's Windows x64 unwind definitions:

  • https://github.com/llvm/llvm-project/blob/main/llvm/include/llvm/Support/Win64EH.h

Inspect the exact upstream version and relevant code before relying on it. External source is a reference for semantics, not permission to copy large implementations without understanding their applicability and license.

7.1 UNWIND_INFO structure

Verify:

  • Version and flags bitfields.

  • Prolog size.

  • CountOfCodes.

  • Frame register and scaled frame offset nibble order.

  • Unwind code array boundaries and alignment.

  • Optional exception-handler data.

  • Chained unwind information.

  • Image-relative addressing.

  • Validation of truncated or malformed records.

A crucial invariant is that CountOfCodes represents the number of unwind-code slots, including operand slots required by multi-slot operations. It does not count only the number of logical operations.

The parser and unwinder must consume each operation's required slots correctly. The alignment rule for the optional data following the array must be honored.

7.2 Opcode coverage

Audit and test all relevant defined x64 unwind opcodes, including:

  • UWOP_PUSH_NONVOL

  • UWOP_ALLOC_LARGE

  • UWOP_ALLOC_SMALL

  • UWOP_SET_FPREG

  • UWOP_SAVE_NONVOL

  • UWOP_SAVE_NONVOL_FAR

  • UWOP_EPILOG, where applicable to the supported unwind-information version

  • UWOP_SPARE_CODE

  • UWOP_SAVE_XMM128

  • UWOP_SAVE_XMM128_FAR

  • UWOP_PUSH_MACHFRAME

Verify opcode numeric values, OpInfo, additional slot consumption, offset scaling, register restoration, and invalid combinations against the appropriate specification version.

Do not infer the existence or meaning of a supported operation solely from an enum name. Record which format versions are supported and reject unsupported forms explicitly.

7.3 Prolog and epilog processing

Verify unwind behavior when the instruction pointer is:

  • Inside a prolog.

  • Inside a function body.

  • Inside an epilog.

  • In a leaf function without a function-table entry.

  • In a chained unwind region.

  • At a boundary between functions.

  • In malformed or absent metadata.

Test stack allocation, saved nonvolatile registers, frame-pointer setup, epilog simulation, return-address recovery, and caller-state reconstruction.

7.4 Exception dispatch and context

Verify:

  • Runtime function lookup by instruction pointer.

  • Exception record and machine context construction.

  • Stack-frame and establisher-frame calculations.

  • Handler lookup and language-specific data parsing.

  • Search versus unwind phases.

  • Continuation of the search through caller frames.

  • Context mutation and restoration.

  • Correct resume address and stack pointer.

  • Correct restoration of integer and floating-point state.

  • Chained metadata handling.

  • Deterministic behavior for invalid unwind metadata.

7.5 Regression fixtures

Create or reuse focused fixtures for:

  1. A leaf function.

  2. A function with a small stack allocation.

  3. A function with a large stack allocation.

  4. A function that saves nonvolatile integer registers.

  5. A function using a frame pointer.

  6. Multi-slot unwind operations.

  7. XMM register save/restore.

  8. Machine-frame unwinding, if supported by the execution environment.

  9. Chained unwind information.

  10. An exception thrown and caught in the same function.

  11. An exception propagated across several stack frames.

  12. C++ stack unwinding with a destructor that must execute.

  13. A catch handler that resumes execution and verifies register/stack state.

  14. A malformed unwind record.

  15. A missing function-table entry.

  16. Prolog/epilog boundary cases.

Use a trusted native Windows result as the behavioral reference when available. If native execution is unavailable, record the alternative oracle and its limitations.

Acceptance criteria

  • Every supported opcode and multi-slot layout has a focused test.

  • Context and stack restoration are verified, not inferred from reaching a new address.

  • Exception propagation and handler behavior are tested independently of UPX.

  • The UPX failure no longer occurs at the same first-divergence point for the same reason.

  • Existing C, C++, x86, and x64 regressions remain within the established baseline.

8. Workstream D — C/C++ Runtime and Windows API Compatibility

Audit the actual import requirements of the current test corpus before expanding API coverage.

Historical reports mention work involving:

  • LoadLibraryA

  • ExitProcess

  • GetProcAddress

  • __stdio_common_v*

  • __p__*

  • FILE and standard I/O behavior

Verify which implementations exist in the current source tree, which are connected to the runtime, and which have real tests.

Do not count an API as supported merely because a symbol resolves. Verify the behavior expected by callers.

8.1 DLL loading and symbol resolution

Test:

  • LoadLibraryA and relevant wide-character equivalents, if supported.

  • GetProcAddress by name and ordinal.

  • Reference counts and module lifetime, where applicable.

  • Failure behavior for missing libraries and exports.

  • Forwarded exports.

  • Function-pointer validity and calling conventions.

  • FreeLibrary, if present or required by a concrete target.

Clearly distinguish a missing DLL, missing export, incorrect calling convention, and incorrect function implementation.

8.2 Process and thread APIs

Audit the APIs actually used by the corpus, including process termination, last-error state, process/thread identity, thread-local state, and synchronization primitives.

Add support according to measured demand and architectural design, not as a list of stubs returning success.

8.3 UCRT and standard I/O

Test, where required by the target programs:

  • Standard input, output, and error.

  • Formatted output and input.

  • Integer and floating-point formatting.

  • Buffering and flushing.

  • File open/read/write/close behavior.

  • Error handling and return values.

  • CRT initialization and shutdown.

  • Static versus dynamic runtime dependencies.

  • C++ exception/runtime dependencies.

For __stdio_common_v* and related UCRT entry points, verify the exact signatures, calling conventions, format flags, and varargs forwarding semantics. Do not use a fake success return when the API must produce output or update state.

8.4 API inventory and prioritization

Produce a frequency-ranked inventory of imports from the existing test corpus. Group missing imports by DLL, API family, and semantic root.

Prioritize fixes that resolve a general compatibility requirement across multiple applications. Avoid one-off application-specific patches unless they are explicitly isolated as temporary diagnostic instrumentation.

Acceptance criteria

  • A resolved API passes a direct semantic test.

  • At least one real application uses it successfully.

  • The API is covered by regression tests for its important behavior and failure paths.

  • API coverage reporting distinguishes implemented, stubbed, unsupported, and verified behavior.

9. Workstream E — UPX End-to-End Execution

UPX is an end-to-end compatibility target, not merely a decompression milestone.

First inspect the exact UPX executable, its PE format, imports, sections, relocations, entry-point behavior, and runtime dependencies. Establish whether the tested executable is a supported x86 or x64 artifact.

9.1 Required stages

Record each stage independently:

  1. Original PE parses successfully.

  2. Initial image loads correctly.

  3. Initial imports resolve.

  4. Packed entry point begins execution.

  5. Decompression or unpacking logic executes.

  6. Unpacked code and data are materialized correctly.

  7. Control transfers to the original program entry point, where identifiable.

  8. Any required relocations, TLS initialization, or import repair complete.

  9. Original application initialization begins.

  10. The application performs its intended operation.

  11. It exits or remains active according to its expected behavior.

  12. Output and state are validated.

Not every UPX variant will use identical internals. Determine the actual behavior from the artifact and runtime trace rather than hardcoding assumed addresses.

9.2 Failure classification

For each failure, record:

  • Original executable SHA-256.

  • Architecture and PE metadata.

  • Build and runtime commit.

  • Last known-good stage.

  • First divergent instruction or semantic operation.

  • Register, stack, memory, and exception state as relevant.

  • Whether the failure is an invalid instruction, access violation, unresolved API, incorrect return value, or semantic mismatch.

  • Whether the fault originates in the unpacker, CPU engine, API layer, exception runtime, or test environment.

Do not classify a later crash as a regression fix merely because the crash moved to a new RVA.

9.3 Required UPX tests

Maintain at least:

  • A known-good unpacked executable baseline.

  • A minimal packed executable.

  • A packed C executable.

  • A packed C++ executable with exceptions, if supported by the selected toolchain.

  • A packed executable using runtime APIs.

  • A packed executable with relocation requirements.

  • A representative older x86 UPX executable.

  • The exact current failing UPX target.

Only use artifacts that can be legally obtained and tested. Record the UPX version and build options when known.

Final acceptance criteria

At least one supported packed executable must demonstrate a complete successful execution path with:

  • A recorded binary hash.

  • Reproducible launch command.

  • Evidence that unpacked code actually executed.

  • Observable application behavior matching its expected result.

  • Correct termination or expected ongoing behavior.

  • No hidden skip, hardcoded test-specific success, or substituted fake output.

  • A clean repeat run and passing regression suite.

If the current UPX sample still cannot complete, the issue remains open. Report the exact last verified stage and the next first-divergence root.

10. Workstream F — C++ Exceptions, Landing Pads, and Resume Semantics

Treat C++ exception handling as a complete control-flow and runtime problem.

Investigate the precise exception model and compiler/runtime ABI used by the failing executable. Do not assume that a mechanism implemented for one toolchain is automatically compatible with another.

Audit:

  • Exception registration and dispatch.

  • Exception object construction and lifetime.

  • Type information and catch matching.

  • Catch-all behavior.

  • Stack unwinding and destructor execution.

  • Personality routines and language-specific metadata.

  • Landing-pad control flow.

  • Resume/rethrow semantics.

  • Register and stack restoration.

  • Runtime library dependencies.

  • Behavior when no handler matches.

Focused tests

Build minimal tests for:

  • A throw/catch within one function.

  • Propagation across two and then several functions.

  • A catch by reference and by value, where applicable.

  • A catch-all handler.

  • A destructor executed during unwinding.

  • A nested exception.

  • Rethrowing an exception.

  • A nonmatching handler followed by a matching caller.

  • Normal execution after a caught exception.

  • Correct return values and preserved state after exception recovery.

Where the current issue reports a landing-pad or resume failure, reconstruct the expected control flow from compiler output and runtime metadata. Confirm whether the problem is an incorrect unwind operation, exception personality behavior, landing-pad selection, or context restoration.

Do not “fix” a crash by skipping exception code, forcing a catch result, or redirecting execution to a known address.

13. Workstream I — First-Divergence Diagnostics

The runtime should help identify the earliest incorrect semantic event, not merely the final crash.

Inspect existing diagnostics before extending them.

Where feasible, add or improve structured traces for:

  • Image load and relocation.

  • Import resolution.

  • API entry and exit.

  • CPU exceptions and invalid instructions.

  • Register and stack state.

  • Runtime function lookup.

  • Unwind operation decoding.

  • Exception search and unwind phases.

  • Landing-pad entry and resume.

  • File and standard I/O.

  • Process exit and test timeout.

Tracing must be configurable so normal execution does not become excessively slow or consume large amounts of RAM.

Diagnostic rules

  1. Identify the earliest divergence from expected behavior.

  2. Preserve enough context to reproduce it.

  3. Avoid dumping unbounded memory or logging every instruction by default.

  4. Use bounded buffers and targeted trace windows.

  5. Keep diagnostic instrumentation separate from compatibility behavior.

  6. Confirm that tracing does not itself change the observed outcome.

  7. Do not treat trace volume as evidence of semantic correctness.

When possible, emit a compact structured event containing the test ID, build SHA, process state, instruction pointer, operation, relevant registers, and result.

Acceptance criteria

A failing regression produces a concise report that points to a specific semantic boundary and enough evidence for another engineer to reproduce the problem without repeating the entire investigation.

14. Workstream J — Generalization and Cross-Application Regression

A fix should improve the runtime generally.

For every root-cause fix:

  1. Identify the underlying semantic rule.

  2. Locate all relevant code paths that implement that rule.

  3. Add a minimal focused test.

  4. Add a regression for the original failure.

  5. Run the full available baseline.

  6. Check both architectures where applicable.

  7. Inspect any newly failing tests.

  8. Compare before/after outcomes.

  9. Record collateral effects and limitations.

Use an A/B comparison between the pre-fix and post-fix builds when a reproducible prior build is available.

Do not require a test to pass if the runtime has no supported implementation for that feature; instead, classify the prerequisite honestly. Equally, do not use an unsupported-feature label to conceal a defect in a feature that the project already claims to support.

Anti-patterns prohibited

  • Hardcoded success for a specific executable or RVA.

  • Skipping failing instructions or exceptions without a justified semantic implementation.

  • Faking API return values to get past a crash.

  • Returning placeholder output while reporting real application execution.

  • Counting an executable launch as a successful application test.

  • Treating an increased number of passing tests as sufficient proof when tests were changed to become less strict.

  • Closing a root issue because a downstream failure appeared.

  • Removing x86 coverage to improve x64 statistics.

  • Modifying expected outputs merely to match incorrect runtime behavior.

Inspect all relevant open issues, linked issues, milestones, and recent commits.

Classify each issue as:

  • Verified complete.

  • Implemented but not fully tested.

  • Active and actionable.

  • Blocked by a concrete prerequisite.

  • Duplicate of an existing root issue.

  • Superseded by a newer implementation.

For every proposed closure, link the fixing commit and regression evidence. If an issue is partially complete, update it with the exact remaining work rather than closing it.

For every unresolved issue, identify the next concrete investigation or test. Avoid vague issues such as “improve compatibility” without a reproducible failure and measurable acceptance criteria.

This master issue should coordinate the existing work rather than create redundant sub-issues. Create a new issue only when there is a distinct root cause or a meaningful independent deliverable that cannot be tracked cleanly in an existing issue.

Required artifacts

Do not close this master issue until its final acceptance criteria are met or the project owner explicitly changes the goal.

16. Required Implementation Sequence

Use the following order unless the initial audit discovers a more fundamental blocker. If the order changes, document why.

Phase 0 — Establish truth

  • Verify repository identity and Git state.

  • Read previous reports and issue history.

  • Reconcile claimed commits, binaries, and test results.

  • Confirm the current build and baseline.

  • Inventory the tools and tests already available.

Exit condition: A verified baseline and a short list of real unresolved roots.

Phase 1 — Reproduce the current failures

  • Reproduce the exact UPX failure.

  • Reproduce t08_big_cpp_stl, t09, t10_float_math, t11_abi_deep, and t12_libc_io, if they exist.

  • Confirm architecture and binary hashes.

  • Capture first-divergence traces.

  • Separate API, ABI, unwind, CPU, and environment failures.

Exit condition: Each priority failure has a reproducible test and a defensible root-cause hypothesis.

Phase 2 — Fix the earliest general root

  • Choose the highest-impact root supported by evidence.

  • Implement the smallest general semantic fix.

  • Add a focused regression.

  • Verify the original failure and related tests.

  • Inspect cross-application impact.

Exit condition: The original failure is fixed for the correct reason and regression evidence is available.

Phase 3 — Expand the regression corpus

  • Add missing x86 and x64 fixtures.

  • Cover relevant unwind and runtime API edge cases.

  • Add C/C++ and packed/unpacked tests.

  • Improve repeatability and result reporting.

Exit condition: The relevant compatibility family has measurable, repeatable coverage.

Phase 4 — Complete UPX end-to-end validation

  • Trace the actual unpacking process.

  • Verify transfer into original application code.

  • Verify real application behavior.

  • Fix the next root cause if necessary.

  • Repeat the complete run.

Exit condition: At least one supported UPX-packed executable satisfies the full end-to-end acceptance criteria.

Phase 5 — Generalize, reconcile, and hand off

  • Run the complete regression suite.

  • Reconcile existing issues.

  • Update documentation and the compatibility matrix.

  • Commit and push authorized changes.

  • Record the exact continuation point.

Exit condition: The next agent can resume from a verified, reproducible state.

17. Definition of Done for Each Engineering Task

A task is complete only when all applicable conditions are satisfied:

  • The original failure is reproducible.

  • The root cause is explained with source and runtime evidence.

  • The relevant semantic rule is documented.

  • The implementation is general rather than executable-specific.

  • A focused regression exists.

  • The regression fails against the old behavior when a valid pre-fix build is available.

  • The regression passes against the fixed build.

  • The original application is retested.

  • Related tests are rerun.

  • x86/x64 applicability is documented.

  • The correct binary and source commit are identified.

  • Logs and evidence are retained.

  • Any unsupported cases are explicitly documented.

  • The appropriate existing issue is updated.

  • The commit is identified and its remote status verified when pushing is authorized.

A task may be marked PARTIAL if a valid environmental prerequisite prevents one or more checks. It must not be marked fully complete merely because code was written.

18. Final Deliverables

The campaign must maintain or produce the following, adapting to the repository's existing conventions:

  1. Repository audit: actual HEAD, branch, remote, build hash, and discrepancies with previous reports.

  2. Issue reconciliation: existing issues, statuses, duplicates, completed work, and remaining roots.

  3. Tooling research: available tools, useful upstream implementations, and adoption recommendations.

  4. Architecture-aware test manifest: test IDs, binary hashes, expected behavior, and results.

  5. Focused regression suite: PE loading, CPU/ABI, runtime APIs, unwind semantics, C++ exceptions, and UPX.

  6. First-divergence reports: reproducible failure locations and relevant machine/runtime state.

  7. Compatibility matrix: verified behavior for x86, x64, packed, unpacked, C, and C++ targets.

  8. Change summary: source changes, tests, commits, and regression impact.

  9. Continuation state: the next exact root cause and next reproducible command.

  10. Updated project documentation: commands to build, test, reproduce, and inspect evidence.

Do not fabricate an artifact or claim a file exists until it has been created and verified in the current environment.

20. Immediate Assignment

Begin with Phase 0. Do not start by guessing which historical BUG number is next.

  1. Read this issue in full.

  2. Read the relevant existing issues and their comments.

  3. Verify the actual repository, HEAD, and remote.

  4. Inspect the current source implementation of the loader, import resolver, exception/unwind machinery, and test harness.

  5. Verify which previously reported fixes and test targets actually exist.

  6. Reproduce the current UPX failure and the relevant C++ regression, if available.

  7. Produce the audit and issue reconciliation artifacts.

  8. Select the earliest high-impact root cause supported by the evidence.

  9. Implement and test that root cause using the existing issue when possible.

  10. Continue through the phases without declaring end-to-end success prematurely.

If a prerequisite is unavailable, record exactly what is missing, what was still verified, and what command or environment is needed next. Do not invent results or silently substitute an unrelated test.

Priority: preserve existing x86 compatibility while advancing general x64 execution and end-to-end UPX support. Every improvement must be reproducible, evidence-backed, and useful beyond one executable.

Final project principle: Fix the underlying compatibility law, prove it with a focused test, verify the original application, and then demonstrate that the same fix improves the broader runtime without regressions.
